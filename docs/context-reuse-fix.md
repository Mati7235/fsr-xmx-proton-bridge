# D3D12 legacy context-reuse fix (candidate, not applied)

## Problem

After `patches/0002-shim-context-output.patch`, the two legacy D3D12 exports
(`_INTC_D3D12_CreateDeviceExtensionContext`, `...Context1`) copy device/driver
outputs back **only on the init path**. When the supplied context already
carries a D3D12 half, both return early with `S_OK` and never touch the
caller's fresh structure (`upstream/xess-xmx-linux/shim/src/dll/IgdextApiDll.cpp`,
`else { // We already seem to have a context return S_OK; }` in each of the
three D3D12 functions). A caller that reuses a context therefore observes
success with zeroed outputs. The CPU harness in `tests/test_context_output.py`
characterizes this; it does not fix it.

## Contract decision

Blindly re-running init on a live half would rebind it. The candidate
`patches/0003-shim-context-reuse.patch` (stacked **after** 0002, generated by
`tools/build_context_reuse_patch.py` for the pinned source
`ef39559d26e083ce1bd1353b2e8c86f33c3c264c`) implements, per D3D12 function:

1. **Device identity.** The stored half's `m_pAppDevice` must equal `pDevice`.
   A different device returns `E_INVALIDARG`. A live half is never rebound and
   caller outputs are left untouched.
2. **Requested-version validation.** The caller's requested version must be
   supported by the **granted** version stored at init
   (`INTCExtensionVersionHelper::IsSupported`), otherwise `E_NOINTERFACE` —
   the same code `InitExtensions` uses for unsupported versions. Validating
   against the granted contract (not the build maximum) keeps a live
   context's contract stable: a lower request still succeeds, a higher one
   fails instead of silently upgrading the half.
3. **Deterministic refresh.** Re-run `InitExtensions` on the live half into a
   zeroed temp (same device, so the rebind is a no-op) and copy the outputs
   back: with the 0002 helper for the two legacy `INTCExtensionInfo` callers,
   with a full-struct assignment for `Context2` (`INTCExtensionInfo1` is
   already the caller width, including the GMD tail). The granted version is
   saved and restored around the refresh so a lower request cannot silently
   downgrade the live contract. If the refresh fails (e.g. a fallback flip),
   the error is returned, the caller structure is untouched, and the half
   stays alive.

D3D11 halves have the same early-return shape but write directly into the
caller struct (no width adaptation); they are out of scope and unchanged.

## Why this shape

- No new stored state and no header changes: the patch touches only
  `shim/src/dll/IgdextApiDll.cpp`, reusing the 0002 copy helper. The outputs
  are re-derived from the same deterministic initializer instead of cached.
- `result` (already in scope), `FAILED`, `E_INVALIDARG`, `E_NOINTERFACE` and
  `INTCExtensionVersionHelper` are all available through `Stdafx.h`; the
  candidate compiles under the same cross-build as 0002.
- Behavior change is deliberate: compatible reuse keeps `S_OK` **and** now
  fills outputs; incompatible reuse fails instead of returning a silent `S_OK`
  with zeroed outputs. Callers that relied on the silent path (e.g. combined
  `_INTC_CreateDeviceExtensionContext` flows create the D3D12 half fresh, so
  they are unaffected) must handle the new errors.

## Verification (CPU only)

`tests/test_context_reuse.py`, against the pinned source and real header:

- builder determinism, source/revision pin, `build_full == build∘build_output`;
- `patch -p1` stack `0002 -> 0003` in an isolated tree;
- Windows ABI layout asserts (192/200-byte structs, output offsets);
- host executables compiling the **actual generated bodies** with stubs that
  emulate the initializer: init, reuse with fresh struct (same/lower
  version), higher-version and foreign-device rejection with untouched
  callers, live-half failure with surviving context, granted-version
  stability, and Context2 full-width refresh including `GMDID`/`XeCoresCount`.
  The same harness run against the original bodies exits `6` (reuse without
  refresh), proving the characterization is not vacuous.

No DLL is executed, no prefix or driver is touched. The patch remains a
candidate: not installed in upstream, a prefix, or a game.
