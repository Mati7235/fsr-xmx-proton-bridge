## Observed sequence

1. First attempt without shim: abort

3. Saved `evidence/vkd3d-trace2-20261112.log`
   (`8894270d…`, 7,775,448 B, 50,417 lines).

## Findings from the log and artifacts

- No Cabinet abort: the 6 LZMS packs loaded via the shim.
- `d3d12_resource_SetName: FSR4 resource detected` (vkd3d workaround
  active, dozens of occurrences).
- `ANV CM: compiling kernel 60..76, 103..111` (~26 compilations,
  toolchain gen `0913d3f4` of the installed bridge, NOT our
  `912cda6a`/`3ddd809f`).
- `ANV CM: ...e8fca351200197b3_e20b_0913d3f4.cmk samples but the
  pipeline layout has 0 static samplers (using linear/clamp)` ×4:
  a kernel with sampling compiled with the sampler fallback.
- The shim dumped 112 kernels (`dyn_0..dyn_111` + `.opt` + `map.txt` +
  `anv_canary`) into `compatdata/pfx/drive_c/igdext_kernels/`.
- **`dyn_60.spv` (358,873 B) is `fsr4_pre_xmx`**: SPIR-V magic, `-vc-payload`
  footer, entry confirmed. The PRE DID get sent to the bridge.
- `dyn_60.opt` is empty (CompileOptions/InternalOptions NULL, as in the
  static analysis).
- `dyn_60.spv` vs offline envelope `ce372719…`: **3 bytes differ**
  (offset 59112–59114): `OpConstant %float %id = 68.45…` (offline)
  → `67.18…` (runtime). A float constant patched by the mod per
  dispatch (probably specialization by resolution/quality), not corruption.
- **No `.cmk` in the cache exceeds 35 KB** (the PRE would need ~360 KB):
  there is no evidence that the PRE was compiled in ANV in this session. Main
  hypothesis for the noise: the PRE never dispatched (or its compilation was
  rejected/silently fell back) and the downstream chain read its output buffer
  uninitialized. Not confirmed: `dyn_60` still needs to be correlated with ANV's
  internal counter and `compile.log` reviewed with timestamps per session.

## What this proves and what it does not

- Proves: the mod→extension→VKD3D→ANV path works end to end with our
  Cabinet shim; the mod sends the real PRE; XMX does real work (timing).
- Does not prove: functional correctness, the PRE's bindings, nor that the
  sampler fallback is the cause of the noise. The overlay and the timing
  are not a verdict.

## Step 1 closed (2026-11-12, post-session)

`map.txt`→cache correlation: `dyn_60.spv` (PRE, 358,873 B) = kernel id
`e8fca351200197b3` = `.cmk` of 30,936 B with magic `CMK2` (format:
header + compiled binary from the zebin, according to the upstream `cmk_pack.py`).
ANV compiled the PRE (`cm-compile ok ... from dyn_60.spv`) and injected it:
the 4 lines `samples but the pipeline layout has 0 static samplers
(using linear/clamp)` ARE the PRE's injection log.

ANV did not reject it explicitly: the bridge fails open (fallback).
The PRE ran on the GPU with: the shim's LWS, the sampler fallback linear/clamp
and an auto-inferred layout (gen `0913d3f4` of the installed bridge, no
profile gate). Suspects for the noise, in order: auto base layout (8) vs the
correct 4 (documented offset), sampler fallback vs dynamic, LWS.
Our patches (0002/0003/0001+registry `3ddd809f`) target exactly this and are not installed.
