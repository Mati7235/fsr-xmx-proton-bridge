# Experimental patches — not installed

`0001-anv-cmk3-explicit-mapping.patch` modifies **the Mesa patch files** of
xess-xmx-linux, not directly an installed driver. It is a second-level patch for upstream
`662dc6e8787c1e9ed43e09ef73733046bc1b8dc3` (2026-11-13). The CMK3 reader is inserted into
upstream's new `anv_cm.c`; the CMK2 path and the layer reader (`layer/src/cmk.c`) remain
intact.

Generation and verification without modifying upstream:

```bash
python tools/build_anv_mapping_patch.py upstream/xess-xmx-linux \
  > analysis/anv-mapping-reproduced.patch
cmp patches/0001-anv-cmk3-explicit-mapping.patch analysis/anv-mapping-reproduced.patch
git -C upstream/xess-xmx-linux apply --check \
  "$PWD/patches/0001-anv-cmk3-explicit-mapping.patch"
```

Regeneration embeds the profile registry digest (`profiles/registry.json`, via
`tools/pre_profile_registry.py`) into `anv_cm_toolchain_gen` in both internal variants:
any change to the registry invalidates cached kernels without altering the global CMK2
path. See `docs/profile-selection-cache-identity.md`.

`.gitattributes` excludes these nested diffs from the whitespace check: their context lines
contain significant spaces. They are validated by regeneration, exact comparison and
`git apply --check`, not by trimming those spaces.

It adds a local CMK3 reader, with an explicit table base and a check of the push size and
the coverage of each DWORD. It keeps the existing CMK2 path. The CMK3 format **is not a
format published by upstream** and requires this reader; do not use its artifacts with an
original driver.

Status: `git apply --check`, syntax of both internal patches, and C validation extracted
with synthetic layouts checked. **Not compiled inside Mesa, not tested on GPU.** Profile
selection by hash and the cache identity bump are offline candidates
(`profiles/registry.json`, `tools/pre_profile_registry.py`); the runtime helper still does
not read them.

`0002-shim-context-output.patch` keeps the shared output-copy helper. Upstream `662dc6e`
already incorporated that copy inline in the two legacy exports; the patch replaces those
copies with the helper so that 0003 can reuse it (the behavior is equivalent).
`0003-shim-context-reuse.patch` extends the output copy to the D3D12 reuse path (it
validates device and version against the granted contract). It is stacked **after** 0002,
generated by `tools/build_context_reuse_patch.py`, and CPU-tested in
`tests/test_context_reuse.py`. See `docs/context-reuse-fix.md`.

Payloads for arguments, local dimensions, samplers and other kernels remain pending. See
`docs/offline-pre-compilation.md`. Do not apply it to the user's session nor install
services/drivers as part of the CPU tests.

`0005-vkd3d-keep-coopmat-extension.patch` modifies **the vkd3d-proton checkout** (worktree
`upstream/vkd3d-proton-coopmat`, base `2576c0b4`, the same revision shipped by Proton
Experimental `experimental-11.0-20261112`), not any installed Proton or prefix. With
`VKD3D_KEEP_COOPMAT_EXTENSION=1` and a driver that advertises `cooperativeMatrix` but does
not pass `vkd3d_supports_minimum_coopmat_caps()` (the ANV Xe2 case on B580: only 8x16x16
f16/bf16 and 8x16x32 s8/u8, missing the required 16x16x16 f16→f32), it keeps
`VK_KHR_cooperative_matrix` enabled on the `VkDevice` (extension + feature as the driver
advertises them, including `cooperativeMatrixRobustBufferAccess` if the driver supports
it) for interop consumers that share the device (e.g. the Apex Neural Rendering FG via
OptiScaler). Everything that would expose WMMA to D3D12 stays off as if the gate had
failed: the float8/coopmat2 features, `SupportsAGSExtension(WMMA_FP8)` and the validation
of the meta `USES_COOPERATIVE_MATRIX` use the new flag `supports_minimum_coopmat_caps`
instead of the raw bit, and the WMMA_FP8 target extension of vkd3d-shader still requires
`shaderFloat8CooperativeMatrix` (unchanged). Without the variable, the behavior is the
original.

Verification without touching the base checkout (`upstream/vkd3d-proton` remains at
`ef9a02e`, intact):

```bash
git -C upstream/vkd3d-proton-coopmat stash -q
git -C upstream/vkd3d-proton-coopmat apply --check \
  "$PWD/patches/0005-vkd3d-keep-coopmat-extension.patch"
git -C upstream/vkd3d-proton-coopmat stash pop -q
```

x86_64-only build in `build/vkd3d-coopmat/` (its own llvm-mingw cross file, meson from the
local `.venv`); DLLs ready in `build/vkd3d-coopmat/dist/`. See
`build/vkd3d-coopmat/BUILD.md`. **Not installed in any prefix.**

`0006-vkd3d-load-amdxc-env.patch` (P0 probe, 2026-11-22) adds an opt-in branch in
`d3d12_device_init_vendor_hacks`: with `VKD3D_LOAD_AMDXC=1` it calls
`LoadLibraryA("amdxc64.dll")` without checking the `vendorID`, so that the local shim in
the disposable prefix is loaded before `amd_fidelityfx_framegeneration_dx12.dll` looks for
it with `GetModuleHandleA/W` (the original hack only loads it for `0x1002`). It only loads
the DLL: all responses still come from the shim. Without the variable the behavior is
identical.
